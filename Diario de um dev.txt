Dia 1 
1. Começando o projeto
Hoje comecei a estruturar o NF Blog, um blog voltado para ferramentas, construção e bricolagem. A ideia era criar uma interface simples, moderna e com uma identidade visual que combinasse com o tema.

Primeiro montei a estrutura básica do HTML com:
Navbar
Featured Post (post em destaque)
Área do autor
Categorias
Avatar do usuário

A estrutura principal ficou assim:
<nav>
<section class="featured">

2. Escolhendo as cores do projeto
Uma das primeiras dúvidas foi definir a identidade visual.
Eu sabia que queria algo relacionado a ferramentas e construção, então decidi seguir uma combinação de:
Branco para o fundo
Preto para títulos e navbar
Laranja para destaques

Os links ficaram assim:
a {
    color: #E67E22;
}

E a navbar:
nav {
    background-color: #1A1A1A;
}


O resultado ficou bem mais profissional do que usar apenas preto e branco.


3. Problema na navbar

Em determinado momento tentei mudar a cor da navbar e nada acontecia.

Depois de investigar, percebi que estava usando:

color: #1A1A1A; (achando que isso mudaria o fundo)

Mas color altera apenas o texto.


A correção foi:

background-color: #1A1A1A;


Depois disso a navbar ficou exatamente como eu queria.


4. Avatar e menu de perfil

Adicionei um avatar na navbar e resolvi deixar ele mais destacado usando a cor principal do projeto.

.avatar {
    border: 0.3rem solid #E67E22;
}


Também implementei um menu suspenso para o perfil.


Inicialmente ele fica escondido:
visibility: hidden;
opacity: 0;


E aparece quando o mouse passa sobre o avatar:
.nav__profile:hover > ul {
    visibility: visible;
    opacity: 1;
}


Foi uma das primeiras partes que realmente começaram a deixar o site com cara de projeto de verdade.


5. Destaque do botão Logout

Achei que o botão de logout precisava chamar mais atenção.

Então usei uma cor laranja mais avermelhada:

.nav__profile ul li:last-child a {
    background: #D35400;
}


Ficou bem mais fácil identificar a ação de sair da conta.


6. Criando os botões de categoria

Depois comecei a trabalhar nas categorias dos posts.

Criei a classe:

.category__buttons {
    background-color: #ECECEC;
    color: #E67E22;
}


E também um hover:

.category__buttons:hover {
    background-color: #E67E22;
    color: #ECECEC;
}


A ideia era fazer parecer uma etiqueta de categoria.


7. Problema que me fez perder um tempinho

Mesmo depois de criar o CSS, as categorias não mudavam de cor.

Atualizei a página várias vezes e nada.

Depois descobri o motivo:

No CSS eu tinha:

.category__bottons


Mas no HTML estava:

class="category__button"


Um simples "s" faltando.... uma vontade de jogar o pc da janela...



8. Construindo a seção Featured Post

Comecei a montar o post principal da página.

Estrutura:
<section class="featured">

Dentro dela:

<div class="featured__container">

Com:
Imagem
Categoria
Título
Texto
Autor

Foi nessa etapa que o site começou a parecer realmente um blog.


9. O problema que mais me deu dor de cabeça

Em um momento percebi que o layout não estava ficando como eu imaginava.

A imagem e o texto não estavam organizados corretamente.

Fui revisar o CSS e encontrei isso:

grid-template-columns: repeat(1fr, 1fr);


O problema é que essa sintaxe está errada.

A correção foi:

grid-template-columns: 1fr 1fr;


Além disso adicionei:

gap: 4rem;
align-items: center;


Depois dessa mudança o layout finalmente ficou organizado em duas colunas.

Foi um daqueles momentos em que uma única linha de código resolve um problema enorme.


10. Efeito hover na imagem

Queria adicionar um pequeno efeito visual quando o usuário passasse o mouse na imagem.

Usei:

.post__thumbnail img:hover {
    filter: saturate(0);
}


Agora a imagem perde a saturação quando recebe hover.

É um detalhe simples, mas deixa o site mais interessante.


11. Moldura da imagem

Achei que a imagem precisava de mais destaque.

Então adicionei:

.post__thumbnail {
    border: 1rem solid #1d1d1d;
}


O resultado ficou com uma aparência mais robusta, combinando com a temática de ferramentas e construção.

Também apliquei:
border-radius: var(--card-border-radius-2) 0;

Isso ajudou a deixar o visual mais moderno sem perder a sensação de algo sólido e profissional.


Algumas coisas que aprendi durante o primeiro dia:

Um único caractere errado pode quebrar todo o CSS.
Nem sempre o problema é complexo; às vezes é só um detalhe.
O inspetor do navegador é um dos melhores amigos de quem programa.
Grid é extremamente poderoso quando configurado corretamente.
Pequenos ajustes de cor fazem uma diferença enorme na aparência final.

Dia 3
Começando e errando já

1. Configurando os posts da página inicial
Comecei criando o CSS para organizar os posts em sequência na página inicial:
css
.posts__container {
    display: grid;
    grid-template-columns: repeat(3, 1fr);
    gap: 5rem;
}

A questão é que não funcionou. E o motivo não era o CSS, mas sim o HTML.
Eu tinha criado vários grids separados:

html
<section class="posts">
    <div class="container posts__container">
        <article class="post">
            ...
        </article>
    </div>
</section>

<section class="posts">
    <div class="container posts__container">
        <article class="post">
            ...
        </article>
    </div>
</section>

<section class="posts">
    <div class="container posts__container">
        <article class="post">
            ...
        </article>
    </div>
</section>

O que, na prática, era a mesma coisa que:
- 1 section
    - 1 container
        - 1 post
- 1 section
    - 1 container
        - 1 post
- 1 section
    - 1 container
        - 1 post

E por que não funcionava?
Porque o Grid só organiza os elementos que estão dentro dele.
Por exemplo:

html
<div class="posts__container">
    <article class="post"></article>
    <article class="post"></article>
    <article class="post"></article>
</div>

Nesse caso, o Grid cria três colunas para três itens.
Já no meu código, cada grid possuía apenas um único post. Então era como se ele criasse: Post 1 | vazio | vazio

Como resolvi?
Transformando isto:
html
<section class="posts">
    <div class="posts__container">
        <article></article>
    </div>
</section>

<section class="posts">
    <div class="posts__container">
        <article></article>
    </div>
</section>

<section class="posts">
    <div class="posts__container">
        <article></article>
    </div>
</section>

Nisto:
html
<section class="posts">
    <div class="posts__container">

        <article></article>
        <article></article>
        <article></article>
        <article></article>
        <article></article>
        <article></article>

    </div>
</section>

Agora existe:
* 1 section
* 1 container Grid
* Vários posts dentro dele

Em resumo, o CSS estava correto desde o início. O erro era estrutural no HTML: cada post estava dentro de um grid diferente. A solução foi colocar todos os `<article class="post">` dentro de um único `.posts__container`, permitindo que o CSS Grid organizasse os cards em três colunas.

2. Criando a seção dos posts
Essa parte foi tranquila. Utilizando as categorias e assuntos criados ontem, consegui montar alguns posts para servir de base para o layout do blog.
Só teve um detalhe: as bordas das imagens estavam muito grossas, e os botões de categoria estavam muito afastados da imagem e muito próximos do título.
Para corrigir as bordas, alterei isto:

css
.post__thumbnail { /* ======== Borda da imagem ======== */
    border-radius: var(--card-border-radius-2) 0;
    margin-bottom: 1.6rem;
    border: 0.7rem solid #1d1d1d; /* antes era 1rem */
}


O valor de `1rem` deixava a borda exageradamente grossa. Com `0.7rem`, o resultado ficou mais equilibrado.

Ajustando os botões de categoria
Para melhorar o espaçamento dos botões, bastou adicionar `margin-top` e `margin-bottom`:
css
.category__buttons {
    background-color: #ECECEC;
    color: #E67E22;
    display: inline-block;
    padding: 0.5rem 1rem;
    border-radius: var(--card-border-radius-2);
    font-size: 0.8rem;
    font-weight: 600;
    text-align: center;
    margin-top: 0.1rem;
    margin-bottom: 1rem;
}

O detalhe importante é que essa alteração precisa ser feita diretamente na classe `.category__buttons`, porque assim todos os botões de categoria do blog serão atualizados automaticamente.


Considerações finais
Gostei bastante do progresso. Ainda falta muito trabalho pela frente, mas ver o layout começando a tomar forma é motivador.

Maior aprendizado do dia
* padding → controla o espaço dentro do elemento.
* margin → controla o espaço fora do elemento.
* border → controla a espessura da borda.
* gap → controla o espaço entre itens de um Grid ou Flexbox.

Hoje ficou claro que nem sempre o problema está no CSS. Muitas vezes a estrutura do HTML é que impede tudo de funcionar como esperado.
E por hoje é só, crianças.

!!!!! Baugulho que me fez suar um pouco !!!!!

Inicialmente, o texto do copyright não ficava centralizado corretamente, mesmo utilizando text-align: center.
O problema era que o .footer__copyright estava dentro do .footer__container, que utiliza um Grid com quatro colunas.
Por causa disso, o elemento ocupava apenas uma das colunas do Grid, e não toda a largura disponível.
Para resolver, foi necessário "forçar" o elemento a ocupar da primeira até a última coluna:

css
.footer__copyright {
    grid-column: 1 / -1; /* Adicionado */
    text-align: center;
    margin-top: 3rem;
    color: #E67E22;
}


Com isso, o elemento passou a utilizar toda a largura do Grid e o alinhamento central funcionou exatamente como esperado.


O que aprendemos hoje?
Eu percebi mais uma vez que nem todo bug visual é culpa do CSS.
Passei um tempo tentando entender o que estava acontecendo, mexendo aqui e ali, para no final descobrir que o problema era simplesmente uma tag que não tinha sido fechada.
Moral da história: antes de ficar quebrando a cabeça no CSS, vale a pena dar uma olhada no HTML. Às vezes você acha que encontrou um bug super complicado, mas era só uma tag esquecida no meio do código fazendo a maior bagunça.

O primeiro tipo de erro estava nas três páginas com formulário.

Nos arquivos add-category.html, edit-category.html e signin.html existia uma div com a classe form__control sendo aberta, mas ela nunca era fechada antes do final do formulário.

A estrutura estava basicamente assim:

Unexpected closing tag "form"

A correção nas três páginas foi fechar a form__control no lugar certo:

<form>
    <div class="form__control">
        <button>...</button>
    </div>
</form>

No signin.html essa div também envolve o texto com o link para a página de cadastro, então o fechamento foi colocado depois do <small> e antes do </form>. Agora cada elemento termina dentro do mesmo bloco em que começou.

</src=>

Essa sequência não existe no HTML. src é um atributo da tag <iframe>, não uma tag que precisa ser fechada. O iframe já possuía o fechamento correto logo depois:

</iframe>

Então removi somente o </src=> inválido e mantive o endereço completo do Google Maps, as dimensões, o carregamento lazy e os outros atributos.

Também adicionei um título descritivo ao mapa:

3 — DOIS HELPERS IMPORTANTES CRIADOS EM post-utils.php
========================================================================================================================

Arquivo:

nf_blog/config/post-utils.php

Foram centralizadas duas lógicas que várias páginas públicas precisam usar.

------------------------------------------------------------
postExcerpt()
------------------------------------------------------------

Essa função cria o resumo mostrado nos cards.

Ela faz o seguinte:

1. recebe o body completo do post;
2. remove tags HTML com strip_tags();
3. remove espaços e quebras repetidas;
4. conta caracteres Unicode corretamente;
5. limita o resumo a 220 caracteres por padrão;
6. adiciona “…” quando o texto é cortado.

Exemplo mental:

BODY COMPLETO
“Este é um texto enorme do post...”
        ↓
postExcerpt($body)
        ↓
RESUMO CURTO PARA O CARD

Se eu quiser mudar o tamanho dos resumos de TODOS os cards, o local principal é:

function postExcerpt(string $body, int $maxLength = 220)

Trocar 220 altera o limite padrão.

------------------------------------------------------------
postDisplayDate()
------------------------------------------------------------

Essa função recebe a data do MySQL e transforma somente a exibição.

O banco continua guardando algo parecido com:

2026-09-26 14:30:00

O visitante vê:

26/09/2026 - 14:30

Se eu quiser mudar o formato das datas públicas, devo procurar por:

function postDisplayDate(string $createdAt)

e alterar:

date('d/m/Y - H:i', $timestamp)

nf_blog/blog.php

5 — post.php VIROU A PÁGINA REAL DE UM POST
========================================================================================================================

Arquivo:

nf_blog/post.php

A rota funciona assim:

post.php?id=5

O número 5 é o ID do post no banco.

Como esse ID vem da URL, ele é uma entrada externa e não pode ser confiado automaticamente.

O fluxo agora é:

$_GET['id']
      ↓
validar se é inteiro positivo
      ↓
prepared statement
      ↓
buscar post + categoria + autor
      ↓
montar a página

IDs ausentes, inválidos, negativos, zero ou inexistentes retornam HTTP 404 e mostram:

“Post não encontrado.”

A consulta usa:

WHERE p.id = ? LIMIT 1

O ponto de interrogação é preenchido com bind_param().

Isso mantém o valor separado do SQL e impede SQL injection.

A página mostra:

- título real;
- categoria real e clicável;
- autor real;
- avatar real ou padrão;
- data real;
- thumbnail real;
- conteúdo completo.

O body é texto simples. Por segurança ele usa:

nl2br(authEscape($post['body']))

authEscape() impede que HTML ou JavaScript armazenado no body seja executado.
nl2br() transforma as quebras de linha em quebras visuais no navegador.

Portanto, se alguém salvar:

<script>alert(1)</script>

o navegador deve exibir esse texto, não executar o script.

6 — category-post.php VIROU UMA LISTAGEM REAL POR CATEGORIA
========================================================================================================================

Arquivo:

nf_blog/category-post.php

A rota funciona assim:

category-post.php?id=2

O fluxo possui DUAS consultas preparadas.

PRIMEIRA CONSULTA:

Busca a categoria pelo ID.

Ela confirma:

- se a categoria existe;
- qual é o título;
- qual é a descrição.

SEGUNDA CONSULTA:

Busca somente os posts que possuem:

WHERE p.category_id = ?

Por que fazer em duas partes?

Porque existem dois estados diferentes:

1. CATEGORIA NÃO EXISTE
   Resultado: HTTP 404 + “Categoria não encontrada.”

2. CATEGORIA EXISTE, MAS AINDA NÃO TEM POST
   Resultado: HTTP 200 + “Ainda não existem posts nesta categoria.”

Uma categoria vazia não é um erro. Ela é uma categoria válida sem conteúdo naquele momento.

Os cards usam os mesmos helpers do blog:

- postExcerpt();
- postDisplayDate();
- authEscape();
- ROOT_URL.

Assim evitamos escrever a mesma lógica várias vezes.

7 — index.php VIROU UMA HOMEPAGE DINÂMICA
========================================================================================================================

Arquivo:

nf_blog/index.php

Somente as partes editoriais foram transformadas em dados do banco.

Navbar, identidade visual, footer, CSS e conteúdo institucional foram preservados.

A homepage possui dois tipos de conteúdo:

1. POST PRINCIPAL EM DESTAQUE
2. CARDS DE POSTS RECENTES

------------------------------------------------------------
COMO O DESTAQUE É ESCOLHIDO
------------------------------------------------------------

Primeiro o sistema procura:

WHERE p.is_featured = 1
ORDER BY p.created_at DESC
LIMIT 1

Portanto, se vários posts estiverem marcados como destaque, o mais recente deles vence.

Se não existir nenhum post com is_featured = 1, o post mais recente do banco vira o destaque.

A ordem é:

1. destaque mais recente;
2. se não houver destaque, post mais recente geral;
3. se não houver post algum, estado vazio.

------------------------------------------------------------
COMO OS POSTS RECENTES SÃO ESCOLHIDOS
------------------------------------------------------------

O layout original possui espaço para até sete cards recentes.

O código busca até oito candidatos porque um deles pode ser o mesmo post usado no destaque.

Depois ele:

- ignora o ID já utilizado no destaque;
- adiciona os outros em ordem de data;
- para quando chegar a sete cards.

Isso evita mostrar o mesmo post duas vezes na homepage.

Se eu quiser mudar a quantidade de cards da home, preciso revisar em index.php:

- o LIMIT 8 da consulta de candidatos;
- a condição count($recentPosts) === 7.

Exemplo: para mostrar 5 cards, provavelmente seriam buscados 6 candidatos e o limite final seria 5.

8 — BUSCA PÚBLICA IMPLEMENTADA
========================================================================================================================

Arquivos:

nf_blog/blog.php
nf_blog/search.php

Foi procurado todo campo de pesquisa público do projeto.

O único formulário de busca real estava em blog.php.
O bloco chamado search__bar em category-post.php é apenas uma área visual para o título da categoria,
não é um formulário de pesquisa.

O formulário de blog.php agora envia:

method="GET"
action="search.php"

e o input usa:

name="q"

Por isso uma pesquisa aparece na URL assim:

search.php?q=furadeira

GET foi usado porque uma pesquisa pode aparecer na URL, ser copiada, atualizada e compartilhada.

Como ainda não existia uma página de resultados, foi criado:

nf_blog/search.php

Ela usa o mesmo visual dos cards de blog.php.

------------------------------------------------------------
VALIDAÇÃO DA PESQUISA
------------------------------------------------------------

O termo vem de:

$_GET['q']

O PHP verifica:

- se q existe;
- se é uma string;
- trim() para remover espaços das pontas;
- se o texto é UTF-8 válido;
- limite máximo de 200 caracteres;
- se não ficou vazio.

Se estiver vazio, a página mostra:

“Digite algo para pesquisar.”

E NÃO executa:

LIKE '%%'

Isso é importante porque LIKE '%%' combina com tudo e devolveria todos os posts sem necessidade.

O limite principal pode ser alterado em search.php nesta constante:

const SEARCH_MAX_LENGTH = 200;

O input HTML também possui maxlength, mas a validação que realmente protege é a do PHP.
O HTML pode ser burlado; o servidor não.

------------------------------------------------------------
CONSULTA DA BUSCA
------------------------------------------------------------

A parte principal é:

WHERE p.title LIKE ? OR p.body LIKE ?
ORDER BY p.created_at DESC

O PHP monta:

%TERMO%

e envia o mesmo padrão para os dois pontos de interrogação usando bind_param().

Os símbolos % significam que o termo pode aparecer no começo, meio ou fim do texto.

Exemplo:

pesquisa = ferramenta

pode encontrar:

“Guia de ferramentas”
“Ferramentas manuais”
“Como escolher uma ferramenta elétrica”

A consulta também faz JOIN com categories e users para o resultado conseguir montar o card completo.

Se a pesquisa for válida, mas não encontrar nada, aparece:

“Nenhum post encontrado para esta pesquisa.”

O título da página mostra de forma segura:

Resultados para: "termo"

========================================================================================================================
9 — SEGURANÇA: PREPARED STATEMENT E ESCAPING NÃO SÃO A MESMA COISA
========================================================================================================================

Essa diferença é MUITO importante.

------------------------------------------------------------
PREPARED STATEMENT
------------------------------------------------------------

Protege a CONSULTA SQL.

Usado quando um valor externo entra em uma busca no banco.

Exemplos:

- ID do post;
- ID da categoria;
- termo pesquisado;
- login;
- IDs enviados por formulários administrativos.

O valor fica separado do comando SQL.

Isso protege contra algo como:

' OR 1=1 --

------------------------------------------------------------
authEscape() / htmlspecialchars()
------------------------------------------------------------

Protege a SAÍDA HTML.

Usado antes de mostrar textos na página.

Exemplos:

- título;
- nome do autor;
- categoria;
- resumo;
- descrição;
- termo pesquisado;
- valores usados em atributos HTML.

Isso protege contra algo como:

<script>alert(1)</script>

RESUMINDO:

prepared statement = protege o banco/SQL
authEscape()       = protege a página/HTML

Um não substitui o outro.

10 — TRATAMENTO DE ERROS
========================================================================================================================

As páginas públicas não devem mostrar ao visitante:

- SQL;
- stack trace;
- caminho interno do computador;
- senha do banco;
- detalhes técnicos da exceção.

Em erro inesperado, o comportamento é:

DETALHE TÉCNICO
        ↓
error_log()

MENSAGEM GENÉRICA
        ↓
visitante

Quando apropriado também é enviado HTTP 500.

Já IDs ou recursos inexistentes usam HTTP 404.

Diferença:

404 = o recurso pedido não existe ou o ID é inválido.
500 = aconteceu uma falha inesperada no servidor/banco.
